# Build and release

> What Grunt generates, how to build a distributable, and how the repository ships the plugin and help site.

## Generated artefacts

`npm run grunt` runs `grunt build`, which runs these tasks in order:

| Task           | Output                                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build_wp_css` | `assets/css/shared.css`, `front.css` and `admin.css` from `assets/less/`; `shared.css` is concatenated into front and admin; `front.min.css` and `admin.min.css`. |
| `build_wp_js`  | `assets/js/front.min.js` from `shared.js` and `front.js`; `assets/js/admin.min.js` from `shared.js` and `admin.js`; both minified in place.                       |
| `build_wj_css` | `waymark-js/src/css/*.css` from `waymark-js/src/less/`, concatenated to `waymark-js/dist/css/waymark-js.css`, then `waymark-js.min.css`.                          |
| `build_wj_js`  | Leaflet, the bundled libraries and the Waymark JS sources concatenated to `waymark-js/dist/js/waymark-js.js`, then `waymark-js.min.js`.                           |
| `copy`         | Waymark JS images and fonts copied into `waymark-js/dist/`.                                                                                                       |
| `makepot`      | `languages/waymark.pot` from the plugin sources, with the WordPress.org bug-report URL.                                                                           |
| `build_wp_md`  | `readme.md` generated from `readme.txt`, with the WordPress.org screenshot URLs and content hashes.                                                               |

`npm run grunt:watch` watches the LESS, plugin JavaScript, `readme.txt` and Waymark JS sources. It does **not** run `makepot`; use `npm run grunt` after changing translatable strings. `npx grunt sync_version` copies the `Version` header from [`Waymark.php`](../Waymark.php) into [`readme.txt`](../readme.txt) (`Stable tag`) and [`package.json`](../package.json) (`version`).

Compiled files are committed. Edit `assets/less`, the non-minified `assets/js` sources, `waymark-js/src` and `readme.txt`; do not hand-edit the generated CSS and JavaScript, [`waymark-js/dist/`](../waymark-js/dist/), [`languages/waymark.pot`](../languages/waymark.pot) or [`readme.md`](../readme.md).

## Local distributable

`npm run dist` runs [`scripts/dist.sh`](../scripts/dist.sh). It:

- reads the version from `Waymark.php`;
- checks for `git`, `rsync`, `zip`, `unzip` and a local Grunt install;
- copies tracked files into a staging tree, symlinks `node_modules` and runs `grunt sync_version build` there, so the working tree is not modified;
- applies [`.distignore`](../.distignore) with rsync;
- verifies the staged `Waymark.php` version, `readme.txt` stable tag and translation-template headers;
- writes `waymark-<version>.zip` to the project's temporary working directory and prints the file count, size and SHA-256.

[`.distignore`](../.distignore) keeps the installed plugin free of development-only material: Git and CI files, local tooling, `node_modules`, `package*.json`, `Gruntfile.js`, the LESS sources, `waymark-js/src` and `waymark-js/libs`, `tests/`, `help/`, `docs/`, `scripts/`, the PHPUnit, Playwright and Vitest configs, `*.md`, `.wordpress-org` and the icon PSD. `readme.txt` and the compiled assets are kept.

The script also rejects a zip that contains Markdown, `tests/`, `help/`, `docs/`, `scripts/`, `.distignore` or the icon PSD. The CI deploy job builds its own zip from `.distignore` with rsync rather than calling `npm run dist`; the local script reproduces that output so it can be checked before pushing.

## Help site deployment

[`.github/workflows/deploy-docs.yml`](../.github/workflows/deploy-docs.yml) deploys the help site to GitHub Pages on manual dispatch, and on pushes to `master` that change `help/**`, `waymark-js/dist/**`, `assets/css/front.min.css` or `package.json`. It installs the help site's lockfile with Node.js 24, runs `npm run sync-assets`, generates the static site with `NUXT_APP_BASE_URL=/${{ github.event.repository.name }}/` (so `/waymark-wp/` for this repository), uploads `help/.output/public` and deploys it with `actions/deploy-pages`.

[`help/nuxt.config.ts`](../help/nuxt.config.ts) reads `NUXT_APP_BASE_URL` (default `/`), uses the `github_pages` Nitro preset and loads `@nuxt/content`. `npm run generate` in [`help/`](../help/) produces the same static output locally; set `NUXT_APP_BASE_URL=/waymark-wp/` to reproduce the published base path.

`npm run sync-assets` copies the built `waymark-js/dist` files and `assets/css/front.min.css` into `help/public/assets/`. Run `npm run grunt` first if those sources changed.

## Version bumps

The `Version` header in [`Waymark.php`](../Waymark.php) is the source of truth. A release bump normally touches:

| File                                                | What changes                                                                                          |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| [`Waymark.php`](../Waymark.php)                     | `Version` header.                                                                                     |
| [`readme.txt`](../readme.txt)                       | `Stable tag` is synced by `grunt sync_version`; the changelog and upgrade notice are written by hand. |
| [`package.json`](../package.json)                   | `version` is synced by `grunt sync_version`.                                                          |
| [`languages/waymark.pot`](../languages/waymark.pot) | `Project-Id-Version` is written by `makepot` during `grunt build`.                                    |
| [`readme.md`](../readme.md)                         | Regenerated from `readme.txt` by `grunt build`.                                                       |

Bumping the version also makes `Waymark_Install::update_check()` back up the current `Waymark_Settings` option under the old version and flush rewrite rules on the next admin load. The stable-key migration runs independently and is idempotent.

If admin or Settings UI shown in the WordPress.org screenshots changes, run `npm run screenshots`. It recaptures the canonical images, publishes them to [`.wordpress-org/`](../.wordpress-org/) and refreshes the `?v=` hashes in `readme.md`. `npm run screenshots:check` verifies the published files and hashes without republishing, and `npm run readme:check` checks only the `readme.md` hashes.

## WordPress.org release flow

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on every push to `master` and on manual dispatch:

1. The `deploy` job reads the version from `Waymark.php` and checks whether `tags/<version>/` already exists in the WordPress.org SVN repository.
2. If the tag is missing, it installs dependencies, runs `npx grunt sync_version build`, builds the distributable from `.distignore` and deploys it with the 10up WordPress.org plugin deploy action.
3. It verifies that the SVN tag exists, commits and pushes any changed synchronised release files (`readme.txt`, `package.json`, `readme.md`, `languages/`, `assets/`, `waymark-js/dist`) back to `master`, and creates a GitHub release tagged `v<version>` with the zip attached.
4. If the tag already exists, the deploy job does nothing. The `readme_assets` job then verifies that the stable tag exists in SVN and deploys `readme.txt` and the `.wordpress-org` assets with the 10up asset-update action.

The WordPress.org deploy relies on the `WORDPRESS_USERNAME` and `WORDPRESS_PASSWORD` repository secrets. The help-site workflow references a `github-pages` environment. The secrets and the Pages site configuration are not provisioned by the repository, and no setup steps are documented in it. There is no documented manual SVN step; the workflow performs the deploy.

Manual work that no task covers:

- Writing the changelog and upgrade notice entries in `readme.txt`.
- Recapturing and publishing the WordPress.org screenshots when the UI changes.
- Provisioning the WordPress.org credentials and enabling GitHub Pages for the help site.

For a release, update the `Version` header and the hand-written readme sections, run `npx grunt sync_version build` to refresh the generated artefacts, and run the test suites. Pushing the release commit to `master` hands the deploy and artefact sync to CI.

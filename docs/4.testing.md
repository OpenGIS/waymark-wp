# Testing

> The three suites that cover the plugin, what each one exercises, how to run them, and the i18n parity check.

The PHP and browser suites run against the disposable wp-env environment; Vitest runs in jsdom without WordPress. The PHP and browser suites target the **tests** instance on port **8889**; never run them against the development instance on 8888. The Playwright config rejects a `WP_BASE_URL` containing `:8888`, and the demo seeder also refuses the development instance.

Start wp-env first (`npm run dev`, or `npx wp-env start`). `npm test` does not start it.

## Suite overview

| Suite      | Command            | Environment                              | Covers                                                                                                                                                                                                      |
| ---------- | ------------------ | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Vitest     | `npm run test:js`  | jsdom, no WordPress                      | Waymark JS Viewer and Editor API, editor i18n, description sanitisation and XSS, i18n escaping, locale formatting and stable type keys.                                                                     |
| PHPUnit    | `npm run test:php` | wp-env tests container, port 8889        | Settings (including repeatable values), Map data and guards, revisions, shortcode and Collection rendering, attachment metadata, requirements, stable keys and i18n.                                        |
| Playwright | `npm run test:e2e` | Chromium against `http://localhost:8889` | Admin menu, Settings markup, labels and repeatable rows, marker icon UI, stable type keys, responsive admin layout, RTL layout, locale formatting, the Map editor smoke test and deterministic screenshots. |

Run one suite with its script, or all three in order with `npm test` (`test:js`, then `test:php`, then `test:e2e`).

## Vitest

Config: [`vitest.config.mjs`](../vitest.config.mjs). The environment is jsdom, the setup file is [`waymark-js/tests/setup.js`](../waymark-js/tests/setup.js), and the include pattern is `waymark-js/tests/**/*.test.js`.

The setup loads Leaflet and the bundled plugins, then evaluates the Waymark JS sources in order (`Waymark_Map`, `Waymark_Map_Viewer`, `Waymark_Map_Editor`, `Waymark_Map_Factory`) into the global scope. The tests under `waymark-js/tests/docs/` mirror the library's documented API chapters; the remaining specs cover XSS and sanitisation, editor i18n, i18n escaping, locale formatting and stable type keys.

## PHPUnit

Config: [`phpunit.xml.dist`](../phpunit.xml.dist). The suite is `tests/phpunit`, the bootstrap is [`tests/phpunit/bootstrap.php`](../tests/phpunit/bootstrap.php), and PHPUnit runs inside the tests container:

```sh
npm run test:php
```

The command is `wp-env run tests-cli --env-cwd=wp-content/plugins/waymark-wp phpunit`. The bootstrap loads the WordPress test library bundled with wp-env and the plugin as WordPress would. It also loads the admin meta and revision classes explicitly, because `is_admin()` is false during the test bootstrap.

Prepare the container once after a fresh environment (`wp-env destroy`):

```sh
npm run test:php:setup
```

That installs PHPUnit ^9.6 and the Yoast PHPUnit polyfills in the tests container. `npm run test:php:lint` runs `php -l` over the plugin from inside the same container.

`WP_ENV_PHP_VERSION` and `WP_ENV_CORE` override the container versions, for example to run against the declared PHP and WordPress floor.

> [!NOTE]
> The PHP suite resets the tests database and deactivates the plugin and theme. The Playwright global setup heals that before the browser suite runs.

## Playwright

Config: [`playwright.config.js`](../playwright.config.js). `testDir` is `tests/e2e`, Chromium only, one worker, no retries, and a 15-second test timeout. `baseURL` is `WP_BASE_URL` or `http://localhost:8889`.

Failure artefacts go to the `outputDir` configured in [`playwright.config.js`](../playwright.config.js), a project-local temporary directory: traces are retained on failure and screenshots are taken on failure.

Global setup [`tests/e2e/global.setup.js`](../tests/e2e/global.setup.js) checks that the tests instance answers, reactivates the plugin and Twenty Twenty-Five, and reseeds the demo dataset before any spec runs.

The deterministic screenshot specs import the extended `test` from [`tests/e2e/fixtures.js`](../tests/e2e/fixtures.js), which provides the external-request guard, third-party asset stubs, motion and caret determinism, and tile record and replay. The legacy `map-editor.spec.js` intentionally uses live OSM tiles and does not import the harness; see [`tests/e2e/README.md`](../tests/e2e/README.md).

### Fixtures

- [`tests/fixtures/demo/seed.php`](../tests/fixtures/demo/seed.php) — idempotent seeder for Maps, Collections, Media, Meta, Settings and the demo page.
- [`tests/fixtures/demo/seed-output.json`](../tests/fixtures/demo/seed-output.json) — generated IDs, slugs, permalinks and image URLs used by the specs.
- `tests/fixtures/demo/tiles/` — frozen basemap tiles replayed by the deterministic specs.
- [`tests/fixtures/route.geojson`](../tests/fixtures/route.geojson) — canonical route fixture used to build the demo Map.
- [`tests/e2e/fixtures.js`](../tests/e2e/fixtures.js) — seed lookups, URL helpers and the deterministic test harness.

The WordPress.org screenshot captures are part of this suite. `npm run screenshots` recaptures them, publishes them to `.wordpress-org/` and refreshes the `readme.md` hashes; `npm run screenshots:check` recaptures and verifies the published files and hashes without republishing. See [`tests/e2e/README.md`](../tests/e2e/README.md).

## Help site

The help site has no dedicated automated test suite. Its checks are:

- `cd help && npm run generate` — builds the static site.
- Browser smoke tests of the pages you changed, under both `/` and `/waymark-wp/`.

The live map demos are driven by the hand-authored data in [`help/app/data/demos/fixtures.ts`](../help/app/data/demos/fixtures.ts); no automated suite asserts their rendering.

## Internationalisation check

`npm run i18n:check` runs [`scripts/i18n-check.mjs`](../scripts/i18n-check.mjs) and enforces the key-parity contract for strings shared by PHP, the Waymark JS library and the help-site demos. It is a source check, not a test suite, and it does not run as part of `npm test`.

| Source     | File                                                                          | Role                                                                                                     |
| ---------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| PHP        | [`inc/Helpers/Waymark_Lang.php`](../inc/Helpers/Waymark_Lang.php)             | `Waymark_Lang::get_js_lang()` is the source of the strings injected into `waymark_user_config.language`. |
| JavaScript | [`waymark-js/src/js/Waymark_Map.js`](../waymark-js/src/js/Waymark_Map.js)     | The `language` defaults let the library run without WordPress.                                           |
| Help site  | [`help/app/data/waymarkUserConfig.ts`](../help/app/data/waymarkUserConfig.ts) | Mirrors the defaults for the live demos in `help/content/`.                                              |

The command extracts the keys and values from each source and fails when:

- a key is missing from any of the three sources;
- a key that appears in more than one source has a different value;
- a `waymark_php_lang` key localised in [`inc/Admin/Waymark_JS.php`](../inc/Admin/Waymark_JS.php) is never read in [`assets/js/admin.js`](../assets/js/admin.js), or vice versa.

It prints the key count for each source and exits non-zero with a list of problems. It checks the English source defaults, not translated `.po` files or the generated POT. The parser identifies the PHP array by `function get_js_lang` and the JavaScript defaults by a `language` block containing `action_fullscreen_activate`; keep those anchors in place when editing.

### Adding or renaming a string

- Map UI strings belong in all three sources, with the same English value in each. PHP wraps the value in a gettext helper; the JS and help-site copies are plain defaults.
- Admin-only strings belong in the `waymark_php_lang` array in `inc/Admin/Waymark_JS.php` and must be read as `waymark_php_lang.<key>` in `assets/js/admin.js`. Do not add them to the three map-language sources unless the map library also needs them.
- Rename a key in every place it appears, run `npm run grunt` to refresh `languages/waymark.pot`, then run `npm run i18n:check`.
- Do not translate keys. Stable Type, Meta and group keys are internal identifiers and are outside this contract; translated labels are separate.

CI runs the check in the `test` job of [`.github/workflows/tests.yml`](../.github/workflows/tests.yml) before the suites.

## Running everything

```sh
npm test
```

This runs the three suites in sequence and stops on the first failure. In CI, [`.github/workflows/tests.yml`](../.github/workflows/tests.yml) runs the JavaScript suite, PHPUnit and Playwright on current WordPress with PHP 8.5, repeats PHPUnit on the WordPress 6.4 and PHP 8.3 floor, and validates the video deliverables. It also runs `npm run i18n:check`, `npm run readme:check` and confirms that the generated `readme.md` is up to date.

# Waymark Release Skill

Releases are single-source and CI-driven: edit the version in `Waymark.php`, run the tests, and push. CI syncs the derived files, builds the assets, deploys to WordPress.org and creates the GitHub Release.

## Version bump

The plugin version is single-sourced from the `Waymark.php` header — the only manual version edit:

| File            | What to change                        |
| --------------- | ------------------------------------- |
| `Waymark.php:7` | `Version: X.Y.Z` in the plugin header |

Everything else is derived and handled by CI (`grunt sync_version build`):

- `readme.txt` `Stable tag` and `package.json` version — synced from the header by `sync_version`
- `readme.md` and `languages/waymark.pot` — regenerated by the build
- `assets/css/*` and `assets/js/*` — rebuilt from the LESS and JS sources

Never edit the derived files by hand.

## Pre-release checks

Run the test suite and confirm the results are as expected:

```bash
npm test
```

> [!NOTE]
> `npm test` is the pre-release gate — run it and confirm the full suite is green; no release ships with any test failing. The PHP suite also asserts the release version metadata, so a header bump without a matching `= X.Y.Z =` changelog entry in `readme.txt`, or a `readme.md` that has not been regenerated, fails the gate — run `npx grunt build_wp_md` after editing the changelog.

> [!WARNING]
> `package.json` and `Stable tag` are expected to lag the header before CI runs; `grunt sync_version` derives both from the header. Leave the skew in place — it is not a failed sync. `package-lock.json` is not touched by `sync_version`, and the tests do not assert it.

## Release workflow

1. **Agree the version** with the maintainer (e.g. `1.6.9`).
2. **Edit `Waymark.php:7`** — update the `Version:` line (the only manual version edit), and add the matching `== Changelog ==` entry in `readme.txt`. Regenerate `readme.md` with `npx grunt build_wp_md`.
   - The `== Changelog ==` entry must credit every contributor — everyone who reported a fixed issue, contributed a pull request or supplied a translation — naming both their GitHub and WordPress.org profiles (see [Closing issues and crediting contributors](#closing-issues-and-crediting-contributors)).
3. **Run the tests** — `npm test` (the full pre-release gate: Vitest, PHPUnit and Playwright).
4. **Write the release commit message** — it must carry a closing keyword (`Closes #N`, `Fixes #N`, `Resolves #N`) for every issue the release fixes, so GitHub closes those issues when the commit lands on `master`.
5. **Summarise** — list the changed files for the maintainer to review, stage and commit.
6. **Push to `master`** — CI takes over (see below).

## What CI does on push

`.github/workflows/ci.yml` reads `Version:` from the `Waymark.php` header and checks the WordPress.org SVN `tags/` directory. The gate is the deployed SVN state, not the local readme — an existing tag for that version means the release is already live.

When the tag is absent, CI:

- syncs `readme.txt` / `package.json` versions (`grunt sync_version`)
- rebuilds CSS, JS, `languages/waymark.pot` and `readme.md` (`grunt build`)
- deploys to WordPress.org SVN (including `.wordpress-org/` assets)
- verifies the tag now exists in SVN — a failure stops the job before the sync-back commit and GitHub Release
- commits the synced artefacts back to `master` (`chore: sync release artefacts for vX.Y.Z`)
- creates a GitHub Release tagged `vX.Y.Z`

No manual deploy step beyond the push. When the tag already exists, the deploy job is skipped and only the readme/assets job runs.

## Manual recovery

The sync + build are idempotent and available locally:

```bash
npx grunt sync_version build
```

If CI fails before the deploy step, run the command above, inspect the result, then re-run the workflow from the GitHub Actions tab. The workflow also exposes `workflow_dispatch`, so a failed deploy can be re-run manually — the SVN tag check makes that safe, skipping a version that already deployed. For local development, use `npm run grunt` for a one-shot build or `npm run grunt:watch` to rebuild on change — do not run bare `grunt` (the default task ends with a blocking watch).

## Local distributable

`npm run dist` builds a CI-faithful plugin zip at `temp/waymark-<version>.zip`.

It copies tracked files into a temporary tree, runs `grunt sync_version build`, applies `.distignore`, and zips the `waymark/` folder. The repository is not modified; use the zip to inspect or test-install the distributable.

## Changelog

Every release gets a per-version entry in `== Changelog ==` in `readme.txt`, summarising user-visible changes. Keep the `[View changes on GitHub ...]` link as the section's final line. `readme.md` is regenerated by `grunt build_wp_md`; never hand-edit it.

Add an `== Upgrade Notice ==` entry when the release changes requirements or carries a security or upgrade-impacting message — this is what WordPress.org shows in the update prompt.

## Closing issues and crediting contributors

**Closing issues.** GitHub closes an issue automatically when a commit on the default branch references it with a closing keyword — `Closes #N`, `Fixes #N` or `Resolves #N`. `Refs: #N` links an issue without closing it, so it is the wrong keyword when the release actually fixes the issue. The release commit (the version-and-changelog commit) is the usual place for these keywords, because it is the commit that lands on `master`. An issue fixed by an earlier commit that already carried `Fixes: #N` closes then and needs no second reference. An issue that is only partly addressed must be left open, and referenced in the changelog without a closing keyword.

**Crediting every contributor.** Everyone who reported a fixed issue, contributed a pull request or supplied a translation is credited in that release's `== Changelog ==` entry, and every person is named with **both** their GitHub and WordPress.org profiles, in this form:

```markdown
- Thanks to [@handle](https://github.com/handle) ([WordPress.org profile](https://profiles.wordpress.org/username/)) for reporting issues #12 and #34.
```

- **Both profiles, every person, every release.** A credit carrying only one profile is incomplete.
- **Never guess the WordPress.org username.** It frequently differs from the GitHub handle — GitHub `JoshJourney` is WordPress.org `ljosh`. Confirm it before writing:

  ```bash
  curl -s -o /dev/null -w "%{http_code}\n" https://profiles.wordpress.org/<username>/
  ```

  A `200` confirms the profile; `404` means it does not exist.

- **Never add anyone to `Contributors:` in `readme.txt` to credit them.** That header is the WordPress.org commit-access list, not a credits list — adding a name there grants that account SVN commit rights to the plugin. Credits belong in the changelog.
- **No WordPress.org profile.** Credit the GitHub handle and describe the contribution; do not invent a profile link.
- **Reach.** `readme.md` is regenerated from `readme.txt`, and CI pre-pends the version's changelog section to the generated GitHub Release notes via the `body` input, so one changelog entry carries the credit to the WordPress.org listing, the generated `readme.md` and the GitHub Release.

## WordPress.org assets

`.wordpress-org/` is the canonical asset mirror deployed to the WordPress.org SVN `assets/` directory (banners, icons, screenshots, and the README hero image). The deploy workflow syncs it to SVN with `rsync --delete`.

The readme screenshots are generated from the tested demo data. The managed set is `editor-demo.jpg` plus `screenshot-1.jpg` through `screenshot-21.jpg`:

```bash
npm run screenshots        # capture canonical JPEGs, publish to .wordpress-org/, regenerate and validate readme hashes
npm run screenshots:check  # recapture, then verify canonical vs published bytes and readme hashes
npm run readme:check       # verify managed URLs and files without recapturing
```

Generated `readme.md` image URLs carry a content-hash query (`?v=<first 12 hex characters of the file's SHA-256>`) because GitHub's Camo image proxy caches by URL and cannot be purged. Rewriting the URL when the bytes change is the reliable cache invalidation; `readme.txt` stays unversioned.

Byte-identical captures are a local release gate, not a CI pixel gate: they depend on the pinned Playwright/Chromium build and the local OS font stack. CI only runs the cheap `npm run readme:check` and generated-readme checks. A screenshot refresh should ship with a release, or wait for the SVN asset deploy before expecting the GitHub README to show the new bytes.

> [!WARNING]
> Every asset that should stay live must be present in `.wordpress-org/` — the deploy deletes anything missing. Maintain the full set, not just changed files.

Readme and `.wordpress-org/` changes deploy automatically when the `deploy` job is skipped — the `readme_assets` job commits `readme.txt` and the assets to SVN `trunk` and to the current stable tag (WordPress.org serves the readme from the tag directory, so both must be updated). Version bumps still deploy everything through the `deploy` job.

The readme/assets job first verifies that `readme.txt`'s `Stable tag` exists as an SVN tag.

> [!WARNING]
> Never hand-edit or pre-sync `Stable tag` to a version that has not been deployed. The readme/assets job fails rather than publishing when the stable tag has no matching SVN tag, so a local `Stable tag` ahead of the live release blocks the readme and assets deploy.
